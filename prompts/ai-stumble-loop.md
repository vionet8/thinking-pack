# チームのAIのつまずきを集めて、対策をスキルにして配る仕組み

## 何のために、誰に、いつ、何を材料に

- **ターゲット**: チームの誰かがAIで詰まった・うまくいかなかったことが、本人の中で終わって、
  別の人が同じところでまた詰まっている時間。
- **使う人**: 対策を作る人（改善チーム）と、配られたスキルを使う全員。
- **使う瞬間**: 詰まった直後に記録する。週1回、集まった記録を分けて対策を決める。対策は配られた日から全員が使う。
- **材料**: 詰まった会話の抜粋と、本人の短い答え。
- **測るもの**: 同じ種類のつまずきが、対策を配った後に何件起きたか（再発件数）。

## 考え方

個人の失敗を、全員の手順書（スキル）の更新に変えるループ。FPRLでいえば、1人の違和感（P）を、
原因の意味づけ（R）を通して、チーム全員の基準（F）の更新（L）にする。
事例ベース推論の4つのR（探す→使う→直す→残す）や、失敗を責めない振り返り（ブレームレス・ポストモーテム）と同じ形。
このリポジトリでは1人分で既に回っている（読み違いの失敗 → CLAUDE.mdのルール → ケース049で効くか確認 → 公開リポジトリで職場へ配る）。

```
詰まる → 記録（記録スキル） → 共有の置き場所 → 週1回の仕分け → 対策 → 効くか確かめる → 配る → 再発を数える
                                                   ↑                                          │
                                                   └──────────── 効かなければ直す・古いものは外す ←┘
```

## 失敗しやすい所と手当て

| 失敗しやすい所 | なぜ | 手当て |
|---|---|---|
| 記録が集まらない | 面倒、失敗を見せたくない | 会話の中で1分で終わる記録スキルにする。3問だけ。責めない。「次の人のため」と伝える。件数を人ごとに評価しない |
| 何でもスキルにしてしまう | つまずきの原因はスキルで直るものばかりではない | 下の「仕分け」で、スキルにするのは頼み方・手順の問題だけにする |
| スキルが効かない | 書いただけでは振る舞いは変わらない（ケース049でも、ルールで手順は直ったが解釈のずれは残った） | 元のつまずきの会話を、スキルあり・なしで再現して比べてから配る。合格基準を先に決める |
| スキルが増えすぎる | 似たスキルが増えると、AIが違うスキルを選ぶ・混ざる | 新しく作る前に既存のスキルに足せないか見る。似た説明のスキルを作らない。月1回、効いていない・使われていないスキルを外す |
| 「最新」が行き渡らない | 各自がコピーして古い版が残る | 置き場所を1つにして、そこから配る（管理者による一括配布や、共有のリポジトリ）。版と変更点を書く |
| 社外秘が混ざる | 会話の抜粋に顧客名や数値が入る | 記録スキルで、固有名詞・数値を伏せてから保存する。置き場所は社内の許可された場所だけ |

## 仕分け（週1回、改善チーム）

| 原因 | 例 | 対策の種類 | 担当 |
|---|---|---|---|
| 頼み方・手順 | 前提を渡していない、1回に頼みすぎ | **スキル**（手順書） | 資産化 |
| AIが知らない社内の情報 | 社内の決まり、過去の案件 | **資料**（参照ファイル、検索の対象に入れる） | 資産化 |
| 道具・権限がない | ファイルを読めない、社内の道具につながらない | **環境の整備** | AI戦略 |
| AIの限界 | 計算の誤り、最新情報がない | **使い方の注意**（確かめ方をスキルに書く） | AI調査 |
| AIに向かない仕事 | 判断の責任が重い、材料がない | **使わない判断**を共有する | AI戦略 |

## 記録スキルの下書き（SKILL.md）

```markdown
---
name: ai-stumble-log
description: AIとのやり取りで詰まった・うまくいかなかったときに、その件を次の人のために記録する。
  ユーザーが「うまくいかない」「詰まった」「記録して」「つまずき記録」と言ったとき、
  または同じ頼み直しが3回以上続いたときに使う。
---

# つまずき記録

最初に「責めるためではなく、次に同じことで困る人を減らすための記録です」と伝える。
1回に1問だけ聞く。全体で1分以内。

1. 「何をしてほしかったですか」（1文）
2. 「AIは何をしましたか。どこが期待と違いましたか」
   - この会話の中から、該当するやり取りを1〜2か所引用して見せ、「この部分ですか」と確かめる。
3. 「結局どうしましたか」（候補: 頼み方を変えて解決・自分でやった・諦めた・その他）
   頼み方を変えて解決した場合は、効いた頼み方をそのまま引用する。

保存する前に:
- 顧客名・案件名・人名・数値を「［顧客］」「［数値］」のように伏せる。伏せた結果を本人に見せて確認する。
- 原因の見立てを1つ付ける（頼み方・手順／AIが知らない社内の情報／道具・権限がない／AIの限界／AIに向かない仕事／不明）。
  見立ては仮で、決めるのは週1回の仕分け。

出力（1件1ファイル、共有の置き場所へ）:
日付 / 作業の種類 / してほしかったこと / 起きたこと（引用） / 結局どうしたか / 効いた頼み方（あれば） / 原因の見立て / 使っていたスキル（あれば）
```

## 配り方（管理者でない場合）

失敗事例とスキルは共有フォルダに貯め、各自のClaudeには「共通の指示」を貼ってもらう。

- **CLAUDE.md はチャット画面では読まれない。** CLAUDE.md は Claude Code（開発者向け）が読むファイル。
  チャット画面（claude.ai）で同じ役割をするのは次の2つ。
  - **個人の指示**（設定 → プロフィールの「Claudeへの指示」）: すべての会話に効く。実用上1,500字ほどまで。
  - **プロジェクトの指示と資料**: そのプロジェクトの会話に効く。指示は約8,000字、資料ファイルも置ける。
- **貼ってもらう方式の弱点は、古い版が残ること。** 指示の中身を変えるたびに全員が貼り直す必要がある。
  そこで役割を分ける。
  - 共通の指示には、めったに変わらないことだけを書く（下の本文）。版番号を入れて、最新かを見分けられるようにする。
  - よく変わるもの（対策スキル、失敗事例、頼み方の例）は共有フォルダに置き、使うときに添付する。
- **TeamまたはEnterpriseのプランなら、共有プロジェクトが一番よい。** 作った本人がプロジェクトを
  メンバーや組織全体に共有できる（管理者は要らない）。共有されたメンバーは同じ指示と資料で会話でき、
  会話の中身は共有されない。自分が指示と資料を直せば、全員がその場で最新を使える。
  共有フォルダは、失敗事例の置き場所と、プロジェクト資料の元として使う。

## 配る共通の指示（本文・約900字）

```
【チーム共通の指示 v1（2026-10-01）】最新版は共有フォルダ「AI活用/共通指示」を見る。

1. 動く前に、頼まれたことを一文で言い直す。曖昧なら「〇〇として進めます」と一行で伝えてから進める。
2. 材料にないことを作らない。数値・単位・専門用語は、渡された資料や私の言葉のまま使う。
   分からないことは「不明」と書き、推測したところは推測と明記する。
3. 結論を出す前に「これが間違っているとしたら、どこか」を一つ挙げる。
4. 長い作業や複数の成果物を頼まれたら、最初に全体の手順を示し、区切りごとに結果を見せる。
5. 顧客名・案件名・人名・社外秘の数値が出てきたら、出力の中では伏せ字にする。
6. 私が「うまくいかない」「詰まった」「記録して」と言ったら、または同じ頼み直しが3回続いたら、
   つまずき記録をとる。責めるためではなく、次に同じことで困る人を減らすためと伝え、1問ずつ聞く。
   (1) 何をしてほしかったか (2) AIは何をして、どこが期待と違ったか（該当するやり取りを引用して確かめる）
   (3) 結局どうしたか（効いた頼み方があれば、そのまま引用する）
   固有名詞と数値を伏せ、原因の見立て（頼み方・手順／AIが知らない社内の情報／道具・権限がない／
   AIの限界／AIに向かない仕事／不明）を1つ付けて、次の形で出力する。私が共有フォルダに保存する。
   日付 / 作業の種類 / してほしかったこと / 起きたこと / 結局どうしたか / 効いた頼み方 / 原因の見立て / 使っていた指示やスキル
7. 共有フォルダのスキルや手順書を添付されたら、この指示より、その手順を優先する。
```

- 1〜5は、このリポジトリで失敗から作ったルール（`CORE.md` の頼み方）のうち、仕事で効きそうなもの。
  チームの失敗事例がたまったら、仕分けの結果で入れ替える。
- 6が記録の入口。スキルを入れなくても、この指示だけで記録がとれる。
- 版を上げたら、変更点と理由を共有フォルダの「変更履歴」に1行ずつ書く。

## 対策スキルを配る前の確認

1. 元のつまずきの会話（伏せたもの）を、スキルなしで再現して、同じ失敗が起きることを確かめる。
2. スキルありで同じ場面を試し、先に決めた合格基準を満たすか見る。
3. 関係ない頼みごと2〜3件で、そのスキルが勝手に動かないことを確かめる。
4. 版と変更点（どのつまずきへの対策か）を書いて配る。

## 間違っているとしたら、ここ

- 一番の壁は仕組みではなく、**記録が集まるか**。最初の1か月は、改善チームのメンバーが自分のつまずきを
  率先して記録し、仕分けの結果と配ったスキルをチームに見せて、「記録すると自分が楽になる」を先に示す。
- AIの性能が上がると、スキルが要らなくなることがある。スキルあり・なしの差が消えたら外す。
- 使っているAIの環境で、配り方は変わる。共有プロジェクトが使えるか（TeamかEnterpriseのプランか）、
  チャット画面から共有フォルダを直接読めるか（コネクタが有効か）を最初に確かめる。読めないなら、添付して使う。
- 共通の指示を貼ったかどうかは、本人しか分からない。「v1」などの版番号をClaudeに言わせて確かめる方法を、配るときに伝える。
