# 絶対に作るべき5つのスキル: 汎用テンプレート（資料・図解・文章・動画編集・業務自動化）

**出どころ**: 本人が貼ったもの（2026-10-25）。別のAIが、動画「絶対に作るべき5つのスキル」を元に作った汎用のテンプレート。
動画の題名・チャンネルは未確認。テンプレートの本文はそのまま載せ、Claudeの見立ては最後の節に分けた。

## 何のために、誰に、いつ

- **使う条件**: AIに同じ種類の作業を繰り返し頼むので、毎回の頼み方を固定したいとき。
  例（これに限らない）: 資料やスライドを作る、説明を図にする、自分の口調で文章を書かせる、動画の編集指示を作る、手順書どおりの事務作業をさせる。
- **使い方**: `[ ]` の所を自分の環境に合わせて書き換え、AIの「システムプロンプト」「カスタム指示」「プロジェクトの指示」、またはスキルに登録する。
  出力の例（few-shot）を足すと、出来がそろいやすい。
- **向かない場面**: 1回きりの頼みごと（その場で頼む方が早い）。判断の基準がまだ決まっていない作業（テンプレートに書く中身がない）。

## 1. 資料作成スキル用プロンプト

```
# Role & Purpose
あなたはプロの資料・スライド作成エキスパートです。入力されたテーマやテキスト情報から、用途やトンマナに応じた最適なスライド構成（HTMLスライド / Googleスライド作成用構造化データ）を生成してください。

# Output Constraints & Parameters
1. 用途（以下から自動判定または指定に従う）:
   - 読み物・配布用: 1枚あたりの情報量を多めにとり、補足説明もテキスト化する
   - 登壇・プレゼン用: テキストは最小限とし、キーワードとインパクトを重視する
2. トンマナ・カラー指定:
   - 基本カラー: [自社のコーポレートカラー / モノトーン / ネイビー / ビビッド]
   - デザイン性: 余白を十分に持ち、視覚的階層を明確にする
3. スライド構成規則:
   - 1スライド1メッセージを徹底
   - 結論（結論ファースト）→ 根拠/データ → 具体例 の順で構造化

# Input Context
[ここにスライド化したい元のテキストやテーマを入力]
```

### 1の補足: 動画の画面にあった設定（2026-10-25、本人が送った画面の写しから文字に起こした）

動画の中で、資料作成スキルが選ばせる「用途・トンマナ・色味」の3つの設定が示されていた。テンプレートの1番より具体的なので、ここに残す。
（画面の画像そのものは、話し手が写っている第三者の画面なので載せない）

**用途**（棒の長さ＝1枚あたりの本文量の目安。同じ目盛りで、最大500字）

| 用途 | 1枚の文字量・本文の大きさ | 説明 |
|---|---|---|
| 読み物 | 300〜500字・13px | 話し手なしで、読めば分かる。報告書や事前配布に |
| 配布用 | 〜180字・15px | 読めて、投影もできる。**迷ったらこれ** |
| 登壇用 | 〜40字・20px | 話し手が補う前提で、図を大きく |
| 図解 | 1枚で完結する図 | 記事やSNSに貼る PNG まで書き出す |

**トンマナ**

| 名前 | 見た目 |
|---|---|
| Editorial | 色面の表紙と章扉。端で切れる巨大な英字と数字、太い罫線と段組み |
| Noir | 暗い地に明朝の見出しと細い罫線。水平線と小さな点で締める |
| Blocks | 紙色の地に、円・扇形・半円のタイルを格子に並べる |
| Clean | 内側に置いた角丸の色面に、白いカードを載せる |

**色味**

| 系統 | 名前と色 |
|---|---|
| モノトーン | Ink `#141414` |
| ビビッド | Scarlet `#DC2F22`、Ultramarine `#2D46E0` |
| グラデ | Aurora `#14D3C2 → #C04FE0`、Dawn `#E9DDFF → #D3F5E6` |
| ベーシック | Navy `#1B2F55`、Forest `#1C4D35` |

画面の注記: 「文字と地の組み合わせはすべて、読みやすさの基準（WCAG 2.1 のコントラスト比）を満たすことを確かめています」。

**Claudeが計算して確かめたこと**（WCAG 2.1 のコントラスト比。普通の大きさの文字は 4.5 以上、大きい文字は 3 以上で合格）

| 地の色 | 白い文字 | 黒い文字（Ink） | 使う文字の色 |
|---|---|---|---|
| Ink `#141414` | 18.4 | — | 白 |
| Scarlet `#DC2F22` | 4.7 | 3.9 | 白（合格ぎりぎり。小さい文字や細い書体は避ける） |
| Ultramarine `#2D46E0` | 6.9 | 2.7 | 白 |
| Aurora（始め `#14D3C2`／途中／終わり `#C04FE0`） | 1.9／3.2／3.9 | 9.8／5.8／4.8 | **黒**（白は全体で不合格） |
| Dawn（始め `#E9DDFF`／終わり `#D3F5E6`） | 1.3／1.2 | 14.3／15.8 | 黒 |
| Navy `#1B2F55` | 13.3 | 1.4 | 白 |
| Forest `#1C4D35` | 9.7 | 1.9 | 白 |

画面の「すべて満たす」は、**地の色ごとに文字の色を正しく選べば成り立つ**。グラデの地に白い文字を置くと読みにくい。
（Aurora の「途中」は、始めと終わりの色を単純に半分ずつ混ぜた色 `#6A91D1` で計算した）

### 1を、画面の設定を入れて書き直した版（Claudeの案）

```
# 目的と読み手
この資料は [何のために] 、[誰が] 、[どこで（読む／投影する／登壇で話す／記事に貼る）] 使うものです。

# 用途（1つ選ぶ。迷ったら「配布用」）
- 読み物: 1枚 300〜500字・本文13px。話し手なしで読めば分かるように補足まで書く
- 配布用: 1枚 〜180字・本文15px。読めて、投影もできる
- 登壇用: 1枚 〜40字・本文20px。話し手が補う前提で、図を大きく
- 図解: 1枚で完結する図。PNGまで書き出す
上の4つは例。どれにも当てはまらないときは一番近いものを選び、理由を1行添える。

# トンマナ（例。これに限らない）
Editorial / Noir / Blocks / Clean のどれか、または [自分の指定]

# 色味（例。これに限らない）
[基本の色を1つ]。文字と地の色の組み合わせは WCAG 2.1 のコントラスト比（本文は4.5以上）を満たすこと。
明るい地・グラデの地には暗い文字、暗い地・濃い色の地には白い文字を使う。

# 構成
1枚1メッセージ。結論 → 根拠・データ → 具体例 の順。

# 元の材料
[ここにテキストやメモを入れる]
```

## 2. 図解・視覚化スキル用プロンプト

```
# Role & Purpose
あなたは認知負荷を最小化する図解・可視化のプロフェッショナルです。複雑な概念やテキスト情報を、直感的に理解できる構造化グラフィック（HTML/CSS、SVG、またはMarkdown表現）に変換してください。

# Visualization Guidelines
- 認知負荷の軽減: テキストをダラダラ書かず、概念間の関係性を視覚化する
- 図解パターンの使い分け:
  - 比較・対比: テーブルまたは左右2カラムカード
  - 流れ・プロセス: ステップ型のフローチャート
  - 構造・分類: 樹形図またはマトリックス表示
- デザインスタイル:
  - 参考デザインのトーン: [シンプル / モダン / Webグラフィック風]
  - 視覚的強調: 重要度の高い要素のみコントラストを強くし、それ以外はトーンを抑える

# Input Text
[ここに図解化・視覚化したい解説文章を入力]
```

## 3. 文章執筆スキル（トーン＆マナー再現）用プロンプト

```
# Role & Purpose

# Style & Tone Profile
- 語尾・口調: [です・ます調 / 語りかけ口調 / 専門的でクリアなトーン]
- 口癖・特徴的表現: [「〜ですよね」「要するに」「結論から言うと」など]
- 展開パターン: 結論ファースト（PREP法）をベースとし、具体例を交えて論理的に展開する
- ターゲット読者: [プログラミング・AI学習者 / ビジネスパーソン]

# Output Format
- 記事 / 台本 / 企画書など指定されたフォーマットに合わせて出力すること。

# Topic & Materials
[ここに執筆してほしいテーマやメモを入力]
```

## 5. 業務オペレーション自動化（手順書→AIエージェント化）プロンプト

```
# Role & Purpose
あなたは特定の社内業務を過不足なく遂行する業務自動化エージェントです。以下の業務マニュアルおよび手順に従い、入力データに対して正確な処理を行ってください。

# Operational Workflow
1. 入力データの確認とバリデーションを行う
2. 以下の手順に沿って処理を実行する:
   - ステップ1: [データ抽出・要約]
   - ステップ2: [特定のフォーマット（請求書/レポート/メール文面等）への変換]
   - ステップ3: [人間による最終確認が必要な項目のリストアップ]
3. 例外処理: 情報が不足している場合は、独自判断をせず確認要求を提示すること

# Target Task & Input Data
[処理対象のタスク内容や入力データを入力]
```

元の回答の「次のステップ」: まず、普段の業務で一番時間を取られている作業のテンプレートを1つ選び、AIのシステムプロンプトやカスタム指示に登録して試す。
必要なら出力の例を足す。

---

## Claudeの見立て（テンプレートを使う前に直すとよい所）

1. **Claudeの「スキル」にするなら、「いつ使うか」の説明が要る。** このテンプレートはシステムプロンプトの形で、いつ呼ばれるべきかが書かれていない。
   Claude のスキル（`SKILL.md`）は、先頭の `name` と `description` で呼ばれるかどうかが決まる。`description` には「どういう頼みのときに使うか」と「使わない場面」を書く。
   5番をスキルにする例:

   ```
   ---
   name: sop-to-agent
   description: 業務の手順書（マニュアル）に沿って入力データを処理するときに使う。例（これに限らない）: 報告書の下書き、データの抽出と決まった形への整形、定型メールの下書き。手順書がない作業や、毎回判断が要る作業には使わない。
   ---
   （ここに5番の本文を、手順書の中身に合わせて書く）
   ```

2. **選択肢を「全部」だと読ませない。** 図解の使い分け（比較・流れ・構造の3つ）や `[ ]` の候補は、AIがそれだけだと受け取りやすい。
   「例（これに限らない）」と書き足し、当てはまらないときにどうするか（例: 一番近い形を選び、理由を一言添える）も書く。
3. **役割の一文より、目的・読み手・出力の例の方が効く**（Claudeの見立て）。「あなたはプロの〜です」だけでは出来はあまり変わらない。
   「何のために・誰が読む・いつ使う・何を材料に」と、良い出力の例を1つ入れる方が、出来がそろう。
4. **3番（文章執筆）の材料**: 本人の口調を再現するなら、`thoughts/` の「本人の言葉」（音声入力のままの言い回しを含む）がそのまま口調の材料になる。
   口癖を推測で書くより、本人の文章を3〜5本貼る方が確か。
5. **5番（業務自動化）がこの人の仕事に一番近い。** 「情報が足りなければ独自に判断せず確認を求める」「人の最終確認が要る項目を挙げる」は、
   CAEの自動化のメモの「承認済みの処理を部品にして、AIは組み合わせだけ」「止めて人に見せる点を先に決める」と同じ考え方（`sources/research/cae-workflow-orchestration.md`）。
   チームで使うなら、チームのつまずきの記録から作るスキル（`prompts/ai-stumble-loop.md`）の1本として配れる。
